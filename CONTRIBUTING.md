# Contributing

Thanks for your interest in this project! This repository is my personal portfolio website, so some parts (my bio, projects, and personal content) are not open to change. Still, contributions that improve the quality of the site are very welcome.

Please read the [Code of Conduct](CODE_OF_CONDUCT.md) before participating.

---

### Ways to Contribute

- **Report bugs:** broken links, layout problems, or anything that doesn't work as expected
- **Suggest improvements:** ideas for design, accessibility, or performance
- **Fix typos and documentation:** small improvements are appreciated
- **Improve code quality:** refactors, cleanup, and performance or accessibility fixes

**Not accepted:** changes to personal content such as my biography, résumé details, project descriptions, or contact information.

### Reporting Bugs

Before opening an issue, search existing issues to avoid duplicates. When filing a bug, please include:

- A clear, descriptive title
- Steps to reproduce the problem
- What you expected to happen versus what actually happened
- Your browser, device, and operating system
- Screenshots, if relevant

For security issues, **do not open a public issue.** Follow the [Security Policy](SECURITY.md) instead.

### Suggesting Enhancements

Open an issue describing:

- The problem or opportunity you've noticed
- Your proposed solution
- Any alternatives you considered

For larger changes, please open an issue and discuss it with me first, before investing time in a pull request.

### Pull Request Process

1. **Fork** the repository and clone your fork.
2. **Create a branch** from `main` with a descriptive name:
   ```bash
   git checkout -b fix/navbar-overflow
   ```
3. **Make your changes**, keeping each pull request focused on one thing.
4. **Test your changes** locally on desktop and mobile sizes.
5. **Commit** with a clear message (see below).
6. **Push** your branch and open a **pull request** against `main`.
7. In the description, explain what changed and why, and link any related issue.
8. Be open to feedback. I may request changes before merging.

#### Commit Messages

Write short, clear messages in the present tense. A simple convention works well:

```
fix: correct navbar overflow on small screens
feat: add dark mode toggle
docs: update contributing guide
style: format hero section
refactor: simplify project card component
```

### Guidelines

- Follow the existing code style and project structure
- Keep code readable and add comments where the intent isn't obvious
- Make sure your changes are responsive and accessible
- Don't add unnecessary dependencies
- Don't commit secrets, credentials, or large unoptimized files
- Only submit work you have the right to share, and credit any sources
- If you used AI tools, review the output carefully and mention it in your pull request
